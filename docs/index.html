App research for Composio's AI Product Ops take-home

Almost every app can be built on. The real blocker is a paid plan, not permission.

This covers 65 of the 100 apps (35 are listed under Coverage) across 10 categories: how you log in, whether a developer can get access on their own, what kind of API it has, whether an MCP server exists, and whether an integration can realistically be built. Everything below comes from one agent run plus a checking pass.

What the data says

62 of 65
can be built on

41 are ready as-is, 21 are ready with a caveat. Only 2 was rated blocked and 1 is not an API product at all (a command-line tool).

18 vs 5
paid plan vs approval gate

When something stands in the way it is usually money: 18 apps need a paid plan to get API access, while only 5 sit behind an app review, partner program or enterprise deal.

75%
offer OAuth 2.0

49 of 65. 49 apps list two or more login methods, so an integration layer has to handle several per app, not one.

47 of 65
say they have an official MCP server

That is the agent's reading, and it is the field I trust least: 5 MCP links were flagged as unreachable and only 3 apps in my answer key had an MCP label to check against.

What that means for a tool-integration platform: the hard part of covering these apps is not finding an API. It is the commercial gate in front of it. About 28% of apps would need a customer to be on a paid plan, and 46 of 65 let a developer start self-serve (free or trial). Planning the catalog around who can try it for free tells you more than planning around who has an API.

How the research agent works

  1. Search and read. For each app the agent runs three web searches (API auth docs, how to get credentials and plan limits, official MCP) and opens the best vendor pages. Search and page reading go through Composio (its Tavily tools, called from the Composio Python SDK with my own free Tavily key as a connected account).
  2. Fill a fixed form. Gemini (free tier) reads only that gathered text and fills a strict schema: auth methods, access, API type, MCP status, verdict, blocker, plus the URL and snippet behind each claim. It is told never to guess and to lower its confidence when evidence is thin.
  3. Check the work with plain code. Rules check that the answer agrees with itself, that cited links are alive, that quoted snippets really appear on the page, that an official-sounding claim comes from the vendor's own domain, and that MCP and OpenAPI links respond. 48 of 65 records tripped at least one check; "no vendor source for this field" was the most common (50 times).
  4. Second look. Flagged records (plus a random 15%) go to a verifier pass that re-reads fresh vendor pages and the pass-one answer. This is the step that mostly failed to run, see below.

Where a human was needed

  • Getting a working search tool: Composio's own search toolkit was retired (calls returned 410/404), and Composio Instant would have billed the organisation's balance, so a person had to create a free Tavily account and connect its key.
  • Reading some vendor pages the tools cannot render (JavaScript-only docs for Ramp, Gumroad and others).
  • Building the answer key and spot-checking it (next section).
  • Deciding when to stop: the free model was overloaded for hours, so a person called time on retries.

How accurate is it? First pass vs final pass

How the answer key was made. The key is mostly AI-labelled from vendor docs, with a person confirming a subset. We picked 30 apps spread across the categories. An independent AI check labelled them from vendor documentation (without looking at the agent's answers); 25 apps ended up with at least one label and 5 could not be read. A person then reviewed 7 rows against the vendor pages and corrected or confirmed them (Copper, Help Scout, Aircall, Meta Ads, LinkedIn Ads, Magento (Adobe Commerce), Plaid). The other rows are unreviewed by a human. 18 of those labelled apps were also researched by the agent, so they are what the scores below use.

Hits. The agent is reliable on what kind of API an app has (100% across 17 apps) and no verdict disagreed with the key, but only one verdict had a label, so that says little.

Misses. Login methods are where it goes wrong: only 50% of the 18 scored apps matched exactly. Most misses are the agent listing an extra method (for example both API key and OAuth where the docs describe one). It also got access and blocker wrong for Copper, Aircall and LinkedIn Ads, where the vendor docs are vague and the key had to rely on a person's judgement.

First pass vs final pass. The score moved from 69% to 71%. That gap comes from one changed record (Notion's login methods), so it is not a measured improvement: the verifier completed 9 of its 54 planned re-checks, and the other 45 kept their first-pass answers after the free model returned overload errors. Access, MCP, blocker and verdict were scored on 3, 3, 3 and 1 apps, which is too few to read anything into.

Run it yourself

git clone <repo-url> && cd app-research
pip install -r requirements.txt
# put GEMINI_API_KEY, COMPOSIO_API_KEY (and your Tavily connection) in .env
python -m agent.pass1          # research every app in data/apps.csv, one JSON per app in out/pass1
python -m agent.pass2          # checks + verifier on flagged records, out/pass2
python -m agent.evaluate pass1 pass2   # score against data/gold.csv
python build_site.py           # rebuild this page

Rerunning pass1 only retries apps that failed, so it is safe to stop and resume.

Scope and next steps

  • This run covers 65 of 100 apps; the rest are a rerun away (the pipeline resumes and only retries what is missing).
  • The answer key is small and mostly AI-labelled; 20 rows were confirmed by a person. Growing the human-checked share is the next accuracy step.
  • The MCP field is the agent's reading and was checked on very few apps.
  • The verifier needs a rerun on the 45 records it could not reach. A paid model or an off-peak run would remove the overload problem.
